### E3. 原 venv 未复用的原因（记录决策）

模块 4 原 `.venv`（346MB）建在 `C:\Users\Mechrevo\.workbuddy\binaries\python\versions\3.13.12` 之下
（另一个工具的**托管运行时**），而前三个模块的 venv 建在通用的 `Python314` 目录下。
整体拷进工具箱后，模块 4 会长期依赖那个工具存在——它一旦被清理，工具箱就启动不了，
「整个目录拷走即可用」这条性质会被破坏。因此改为用工具箱同一基础解释器重建，
代价是一次性的装包时间，换来的是全工具箱运行时来源一致。

> 副作用：模块 4 模块名保持不变（`modules\live_recorder\`，目录名即包名，绝对导入依赖它），
> 另有 `main.py` 会把上一级目录插入 `sys.path`，所以 `modules\` 必须作为它的父目录——两条约束都已满足。

## H. 遗留风险（不影响"开箱即用"，如实记录）

1. **抖音单视频下载当前受平台风控**（登录态降权，`filter_reason=core_dep`）：与合并无关（原项目同环境同样失败，已 A/B 实测）。用户重新扫码登录后预期恢复；若平台改版需另行修复。
2. 快手登录态 Cookie 有有效期，过期后点「扫码登录」按钮刷新（已内置流程）。
3. 热榜/搜索等只读接口未登录也能用；搜索接口当前返回 0 条（未登录态平台限制）。
4. **直播录制：不登录快手只能录推荐流覆盖的房间**。快手对未登录访客关闭了按房间查询的接口，
   且对自动化访问以「请求过快」拦截（无头/有头 Chromium、有头真实 Chrome 三种实测全被拦，非指纹问题）。
   登录后可监控任意指定主播；未登录可用「推荐流页数」调大提高命中率（最多 10 页 ≈ 100 房间）。
5. ~~**直播录制：录像目录在工具箱之外**~~ —— **已解决**（2026-09-23 晚，见 I 段）：
   停机后已把 2.1 GB 录像整体迁入 `downloads\live_recorder\`，四个模块产物位置完全统一。
   代价是**删工具箱会连带删掉录像**（已写进《使用说明》§6 与《备份与回滚说明》）。

## J. 无窗口化改造（2026-09-23 20:42–21:10）

起因：双击启动工具箱后，桌面上一直挂着一个黑色终端窗口。

### J1. 定位：黑窗口到底是谁

| 发现 | 证据 | 结论 |
|---|---|---|
| `启动工具箱.bat` 用 `"%PY%" toolbox.py` **前台**运行 | 读 bat 源码 | cmd 窗口会一直挂到工具箱关闭 —— **这是用户看到的主因** |
| `_run_script` **同时**用了 `stdout=PIPE` 与 `CREATE_NEW_CONSOLE` | `toolbox.py` 原第 410–412 行 | 输出本来就已经进日志窗格，再建控制台纯属多余：菜单里每点一次按钮就多一个**空白**黑窗口；更糟的是那个窗口被误关时会连带杀掉子进程（`CTRL_CLOSE_EVENT`） |

### J3. ⚠️ 一个差点造成功能损坏的误判（最值得记录的一条）

**我最初的结论错了。** 在改 `CREATE_NO_WINDOW` 之前，我用
`grep -E "input\( *['\"]|input\(\)"` 检查各模块是否读 stdin，全部返回 0 处，
于是判定「隐藏控制台是安全的」。

实际 `modules\douyin\launcher.py` **确实调用了 `input()`**，只是写法是多行的：

```python
raw = input(
    "\n请粘贴抖音链接或分享口令后回车开始下载"
    "（可一次粘多个，直接回车退出）："
).strip()
```

`input(` 后面直接换行、没有紧跟引号，所以那个正则一条都没匹配到。
**若照原计划直接隐藏控制台，抖音下载器的链接输入会立刻 EOF，功能当场废掉。**

改用宽松模式 `input\(` 重查全部 `modules\**\*.py`，真实结果是：

| 文件 | 是否读 stdin | 说明 |
|---|---|---|
| `modules\douyin\launcher.py:48` | **是** | 唯一的交互式输入点 |
| `modules\douyin\cli\login_flow.py:32` | 隐性依赖 | `sys.stdin.isatty()` 决定能否交互式重登；`sys.stdin is None` 时抛 `AttributeError`，被 `except (AttributeError, ValueError)` 捕获 → 返回 `False`，**安全降级不崩溃** |
| 其余（WebUI / 快手扫码登录 / 直播扫码登录 / 直播自检 / clawfetch） | 否 | `clawfetch.py:97` 的 `isatty` 判的是 **stdout**（决定是否画进度条），与 stdin 无关 |

**修法**：不是给抖音下载器保留控制台（那等于问题没解决），而是利用
`launcher.py` 本来就支持 `sys.argv` 传链接这一点，把入口改成
「界面多行输入框收文本 → 压成单行 → 带参数无窗口启动」。
副作用的处理已在《使用说明》§0.5 写明（交互式重登降级为日志提示，
需要时用带终端的 `启动抖音下载器.bat`）。

> 教训：判断「某程序是否依赖终端」时，正则必须用 `input\(` 这种宽松形式，
> 并在结论写进文档前**逐个打开确认**；多行调用是标准写法，只匹配 `input("` 会漏掉一整类。

### M1. 过程中改掉的实质缺陷

1. **探测图形边界判断漏了范围校验** —— 把 -1 那圈分隔符按「第 0 行/列」涂成深色，
   45 个模块错。靠逐模块比对抓出来（肉眼看不出来）。
2. **分隔符被留成 `None`** —— `None` 在本实现里表示「待写入的数据区」，
   于是数据被写进分隔符。同一轮比对暴露出第二个错。
3. **URL 字符集把冒号排除** —— 端口被截掉，带端口的链接全部失效。
4. **菜单新增按钮把末位顶到折叠线以下** —— 本项目记录过的老毛病复现，已按测量值收敛。
5. **成功任务的备注把 `台账:E:/zl/...` 这类日志碎片发到手机上**，且把本机绝对路径
   播到局域网 → 成功任务不再下发 note，其余 note 里的绝对路径折成文件名。
6. **`启动手机下载.vbs` 是坏的（交付后自查才发现的）** —— 关键行写成了
   `shell.Run  & bat & , 0, False`，四组双引号全丢，wscript 打开即语法错。
   根因见下条。这类错误「文件外观毫无异样」，只有双击才知道。
7. **`tools/gen_launchers.py` 有两处会静默产出坏文件**：
   - `crlf()` 被作用在**编码后的字节**上。UTF-16LE 里换行是 `0a 00`，
     对字节做 `replace(b"\n", b"\r\n")` 会在每个 `0a` 前插一个 `0d`，
     文件多出半个字符、总长变奇数、从插入点起整体错位 → 打开一片乱码。
     已改为先归一文本再编码，并加断言「去掉 BOM 后长度为偶数」。
   - 模板用 Python 三引号包着，源码里连写四个双引号会被当成分隔符吃掉，
     于是 `.vbs` 静默少引号（就是上一条的真因）。已改为占位符 `__Q4__` +
     `chr(34) * 4` 生成时拼装。
8. **自检本身给过假绿灯** —— 原断言只查 `", 0, False" in text`，坏文件照样通过。
   已改为**逐字符比对整行** `shell.Run """" & bat & """", 0, False`，
   并加「产物必须与生成器一致」的守护断言。教训：断言要盯住语义关键片段，
   不能只找「看着像」的子串。
9. **备注净化漏掉 UNC 路径** —— `_RE_WINPATH` 只认盘符路径（`C:\...`），
   `\\NAS\share\...` 会原样播到局域网，把主机名与共享名一起送出去。
   已扩成 `(?:[A-Za-z]:\\|\\\\)...`，盘符与 UNC 一视同仁。
10. **有一条安全断言会随环境静默消失** —— 「任务备注不泄露绝对路径」原本挂在真实
   任务列表上（`if d["tasks"]: ... else: 跳过`），任务列表一空这条就不产出了，
   自检项数从 50 掉到 49 而没人会注意。已改为**喂固定输入的定值用例**
   （直接调 `_tidy_note` / `extract_url` / `detect_kind`），与运行环境解耦；
   同时把线上那条改成无论如何都产出结果。教训：依赖环境的断言等于没有断言。

## N. 抖音「输入链接就秒失败」（2026-09-25 21:23，本轮定位并修复）

### N1. 症状

```

### N2. 根因（一句话）

`modules/douyin/config.yml` 里 `database_path: ../../data/douyin/dy_downloader.db`
是**相对路径**，按 CLI 的 CWD（`modules/douyin` —— 桥接用 `cwd=ROOT` 起进程）解析成
`<工具箱>\data\douyin\`；而该目录当时**不存在**。sqlite 只建库文件、**不建目录**，
于是 `aiosqlite.connect()` 直接抛 `unable to open database file`。

失败点在 `main_async` 的 `database.initialize()`，**早于解析链接** —— 所以是"每条链接
都秒失败"，跟链接、账号、风控都没关系。这一点极具迷惑性：备注里的 sqlite 报错
很容易被当成"平台把请求挡了"。

**反证**（本轮做的对照实验）：把新加的自建逻辑打成空操作后，同一段代码复现出
`OperationalError: unable to open database file` —— 与用户看到的一字不差。

## P. 快手风控 · 批量独占 + 粒度取证（2026-09-25 22:10，本轮）

起因是一个很自然的想法：**「能不能多开几个窗口同时跑，来提速？」**

### P1. 先看清现状：并行早就在了，但不在撞墙的那一段

| 阶段 | 现状 | 并行 | 打接口 |
|---|---|---|---|
| 收集（滚主页） | `dom_collect` 单页面深滚 | ❌ 串行 | ✅ 是 |
| 详情预取 | 主线程逐个 `fetch('/graphql')`，`--sleep 0.25` | ❌ 串行 | ✅ 是（**撞墙就在这一段**） |
| 媒体下载 | `ThreadPoolExecutor(max_workers=4)` 并行 yt-dlp | ✅ 4 线程 | ❌ 不碰接口 |

→ 「并行下载」这个提速点**早就吃掉了**（实测 30 个作品 27.9s vs 串行 118s，约 4.2 倍，
见 `modules\kuaishou\README-快速上手.md`）。剩下的串行段恰好是**唯一不能并行**的那一段。

### P2. 结论：多开窗口不提速，而且更糟

快手这道风控认的是 `did` cookie（设备 ID）。同一登录态的多个窗口 = **同一份身份**，
不是几份额度。多开窗口只做到两件事：

1. **当日额度被各领一份。** 预算是「读-判断-写」，不是原子的：两个进程都读到
   「还剩 400」→ 实际打出去 800。守卫被自己的第二个窗口绕过去。
2. **把温和的串行变成激进的并行。** 而并行猛打正是 09-25 撞墙的形状。

### P4. 三个实现细节（都是踩过才知道的）

1. **判活只用心跳时间戳，绝不用 pid。** Windows 上 `os.kill(pid, 0)` 不是探活，
   它会真的 `TerminateProcess` 掉对方 —— 一个探活函数把目标进程杀了。
   所以是「30s 心跳 + 180s 过期」。副作用正好是想要的：进程被 `taskkill /F` 之后
   租约自动作废，用户不会被残留文件永久卡住。
2. **子进程必须能借用父进程的租约。** `resume` 会把 `fast_dl` 当子进程拉起，
   子进程也会调 `acquire_run` —— 不处理就是「resume 一启动就把自己拦死」。
   做法：父进程把 `current_token()` 塞进子进程环境 `KS_RUN_TOKEN`，
   子进程看到就直接借用（不写文件、不释放）。
3. **心跳线程要记住落点。** 后台线程拿不到调用方的 `explicit`，第一版写死 `None`
   → 会把心跳刷到默认锚点，而真正的租约在别处悄悄过期。加了 `_held_dir` 补位。

### P5. 自己犯的错（记下来）

  后面的注释行反而被当代码扫进来。改用标准库 `tokenize` 剔除 COMMENT / STRING。

## Q. 快手风控 · 「多个 ck 有没有用」（2026-09-25 22:20，本轮）

用户的问题：**「那如果多个 ck 呢，有没有用？」**
（P 章的「多开窗口」答的是同一个身份多开；这一问是多份身份。）

### Q1. 起点：一个必须承认的漏洞 —— 上一轮自己留下的

P 章给批量加了「独占租约」，但**租约和风控状态都是全局一份**。只有一份登录态时这
完全正确；一旦手上有第二份 cookie / 第二个账号，它会以两种方式坏掉：

- 换第二份登录态 → 被**第一份的冷却**拦住。用户会得出「多个 ck 没用」的结论，
  而实际上是**守卫在拦**，不是平台在拦；
- 两份同时跑 → 全局状态只有一份，互相偷额度；或者被**一把全局锁**挡死
  （P 章那把 `run.lock` 会把第二条完全独立的路也堵上）。

所以正确的说法不是「多 ck 没用」，而是**当时的工具还不认识「身份」这个维度**。

### Q2. 技术问题先答清楚：桶该按什么分？—— 按 `did`（设备），不按 `userId`（账号）

读了当前登录 profile 的 **26 个 cookie**，身份字段是**两个各自独立**的 cookie：

| cookie | 长度 | 出现在哪些域 | 同一 profile 里换号登录 |
|---|---|---|---|
| `did` | 36（`web_59262ae3bd02f5…`） | `.kuaishou.com` / `.live.kuaishou.com` | ❌ **不变** |
| `userId` | 10（`5186913760`） | `.kuaishou.com` / `id.kuaishou.com` | ✅ 变 |

（两个域的 `did` 是同一个值；`userId` 三处也是同一个值 —— 说明确实是「一个设备 + 一个账号」。）

**推论**：同一份 profile 里登出再登另一个号 = 同一台设备 = **同一个桶**；
只有换 `--user-data-dir`（新 profile）才会拿到新的 `did`。
→ 「多搞几个 ck」的收益**只在换设备身份时才出现**。

**为什么守卫选 `did` 而不是 `userId` 分桶：猜错的代价不对称。**

| 真实规则 | 按 did 分桶 | 按 userId 分桶 |

| 平台按**设备**判 | ✅ 正确（两个号共用一份额度） | ❌ **等于拆掉刹车**（两号各 400 → 实际 800） |

## R. 直链下载失败（2026-09-26，本轮定位并修复）

用户的问题：**「直链下载失败，查看原因并解决」**。
具体是手机端下发的一条 **818.91 MB** 直链（Clawfetch 模块 3），失败了。

### R1. 现场

手机端那条任务（`.tasks\de0a0dabb3d.log`，220 行）的真实数字：

| 指标 | 实测 |
|---|---|
| 并发数序列 | `[尝试 1/4] 8 个连接` → `[2/4] 8 个连接` → `[3/4] 8 个连接` → **`[4/4] 23 个连接`** |
| 中途自适应 | 只有一行 `[自动] 当前聚合 315.86 KB/s，扩到 16 线程…`，**没有一次"降"** |
| HTTP 502 | **72 次** |
| `30s 无数据` 读超时 | **33 次**（"读取超时"字样共 69 次） |
| 终局 | 退出码 6，`连接/读取超时`；断点（23 段 / 约 26.67 MB）被移进 `.clawfetch_trash\` |

### R2. 三层原因（逐层实测，不是推测）

**第一层：源站侧 —— 卡在"请求发出后不出声"。** 裸 socket 逐层实测：

| 层 | 结果 |
|---|---|
| DNS | ✅ 0.01s，解析到 `104.16.230.132` / `104.16.231.132` |
| TCP 443 | ✅ 0.23s |
| TLS 握手 | ✅ 0.47s，TLSv1.3 |
| **HTTP 响应** | ❌ **6 次里 5 次收不到响应头**（15s 超时），1 次 7.88s 成功返 `206` |

换成 60s 超时再试 3 次：**首字节等待 19.94s / >60s / >60s**；成功那次
拿到响应头后 **0.51s 就交完 256 KiB**（≈0.5 MB/s）。
→ **不是 DNS、不是被墙、不是 TLS、也不是客户端**；首字节延迟在 0～>60s 剧烈抖动。

> ⚠️ **这里原本写的是「818.91 MB 在这种抖动下实际上不可能下完」—— 该结论是错的，
> 已被 R6 的实测推翻。** 错因：把一个 10 分钟的采样窗口当成了永久性质。
> 该源的瓶颈是**突发式限流**：窗口差时三次中不了两次，窗口好时能**连续 25 分钟**不停输出。

**再切一刀：卡的是「文件流端点」，不是隧道、也不是带宽。** 同一源站、同一条隧道换路径：

| 请求 | 结果 |
|---|---|
| `GET /download/<tok>`（HTML 中转页）×3 | ✅ **3/3 成功，首字节 1.04 / 1.15 / 1.43 s** |
| `GET /stream/<tok>` Range 256 KiB ×3 | ◐ 2 成功（首字节 **30.89 / 16.96 s**）、1 在 30s 超时 |
| `GET /stream/<tok>` Range **1 字节** ×2 | ◐ 1 在 **17.09 s** 后返回 1 字节、1 在 30s 超时 |

→ **隧道是活的、HTML 页 1 秒就回**，只有**文件流端点**在卡；而且"只要 1 个字节"
也要等 17 秒 —— **不是带宽问题，也不可能是"多连接互相挤占"**（1 字节没有带宽可言），
而是**文件流处理端自己串行阻塞**。这也解释了"为什么降到单连接也快不起来"：
单连接能做的只是**不被别人的排队连累死**。

**这一层客户端改不了它的速度上限**（但"下不下来"客户端能决定 —— 见 R6）。

**第二层：clawfetch 的"自适应"只会升不会降（已修）。** 旧判据是
`all(s["done"] > 0)` —— 即"每段都滴到过一滴就算健康"。818 MB 的源站上滴速
2 KB/s 也算"健康"，于是 8 → 16 → 23 一路加，把本来能跑完的单连接拖成 502 风暴。
唯一的退路「检测到串行响应 → 回退单线程」还带着两个死结：它靠**丢掉已下进度**换单线程，
而且被 `attempt == 1 and resumed == 0` 锁住 —— **从第 2 次尝试起永远打不开**，
而失败恰恰都发生在第 2 次之后。附带：`--segments N` 在续传时被盘上的 meta 覆盖，
用户照提示加 `--segments 1` 也没用。

**第三层：桥接把"外壳注入的代理"交给了子进程（已修）。** 桥接用
`env = dict(os.environ)` 起子进程，把启动它的那个外壳里的
`HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:12890` 原样继承下去，而 clawfetch 里
5 处裸 `urllib.request.urlopen` 完全按环境变量走 → 「直连这个 URL」变成了
「绕到 127.0.0.1:<别人的端口>」，且**从日志里完全看不出走了哪条路**。
（同文件 `lr_daemon_call()` 里早就为守护进程规避过同一件事 —— 见那里的注释
「HTTP_PROXY 会让 localhost 请求也走代理并 502」—— 只是没管到子进程。）

> 注：本轮把这条链接**直连**与**走那个代理**两条路径都测了，**两条都超时**，
> 所以第三层不是今天这次失败的直接原因 —— 它是**真实存在的隐患**，不是借口：
> 该代理属于启动桥接的外壳，会随它消失；一旦消失而桥接还在跑，
> 子进程就会连到一个死端口，从"偶尔成功"直接变成"全失败"。

### R6.2 这次成功纠正了三件事

1. **源站不是"死了"，是"突发式限流"。** 前 17 次尝试磨了将近 20 分钟才推进 5 MB
   （每次 20s 超时都得重新排队）；第 18 次一进去就**连续给数据 25 分钟**。
   瓶颈形态是「窗口差时频繁归零、窗口好时持续输出」，不是"永久不出声"。
   **我把一个 10 分钟采样窗口当成了永久性质 —— 这是本轮最大的判断错误。**
2. **短超时（`-t 20`）在这里是优点，不是缺点。** 我一度建议"把超时加大到 `-t 90`"——
   那是**反向优化**：卡住的请求要等 90 秒才被放弃，而每次放弃都得重新排队，
   白白降低撞上"好窗口"的次数。**20 秒果断切断 + 立刻重来 + `-n 100` 的预算**才对的。
3. **"进度保留 + 自动续传"是这次能成的真正前提。** 17 次失败累积的 5.94 MB 一滴没丢，
   第 18 次是**从 5 945 920 字节接着下**的。旧代码在第一条逃生门上就 `move_to_trash`
   把这 5.94 MB 丢掉，又因 `attempt == 1 and resumed == 0` 锁死而再不会开第二次逃生门 ——
   也就是说：**旧代码即使"源站心情好"，也很难攒够进度撞上那个 25 分钟的好窗口。**
   （这条是本轮那 12 项改动真正兑现价值的地方。）

### R6.3 顺带解清的两个现场疑问

- **没下完的那份 `.failed` 到底占多少盘**：`GetCompressedFileSizeW` 量出来是
  **818.9 MB**（逻辑 818.9 MB / 实占 818.9 MB），**不是**空洞文件。
  现在真文件已在 `E://zl//`，隔离区那一份是可删的冗余。
  按 clawfetch「**隔离而非删除**」的既定设计，程序自己**不删**；要清就人工清：
  `E://zl//.clawfetch_trash//`。
- **`--segments 1` 续传没有被隔离**：本次从 1 048 576 → 5 945 920 全程续传成功，
  说明盘上那份断点本来就是单线程格式（与 R5 限制 3 的前提一致，不冲突）。

### R6.4 给用户的可复用结论

> 遇到"限流型/隧道型"的不稳定直链，**不要加大超时、不要多线程、不要等"恢复"**：
> ```
> --segments 1 -t 20 -n 100 --backoff 2
> ```
> 短超时快速重排 + 单连接不被挤占 + 进度保留 + 足够重试预算 —— 磨也能磨下来。

### S4 一条操作坑：启动脚本"已在运行就复用"

### S5 批量下载：**先解析、再取名**（中转页链接不再存成 `<id>.bin`）

**症状**：用户粘贴 8 条 `…/download/<id>` 链接（File To Link Bot 分享站），下完发现
文件被存成 `89dd378182be8970.bin` 这种哈希名，而站点页面上明明写着 `9.mp4`。

**根因**：`/download/<id>` 返回的是 **HTML 落地页**（16 KB、`text/html`、chunked、
无 `Content-Length`），真实文件在 `/stream/<id>`。clawfetch 的
`run()` 会自动解析这层（`resolve_html_page()`）→ 没问题；**漏的是并行批量的取名时机**：

| 路径 | 取名时机 | 结果 |
|---|---|---|
| 单条链接 | `run()` 内先解析，解析后**递归重跑**一遍 `run()`，取名用的是直链的 `Content-Disposition` | ✅ 正确（一直是好的） |
| 并行批量 | `run_batch()` 先调 `_preassign_targets()` 预分配目标路径（为避免同名互撞），此刻**还没解析**，HTML 页又没有 `Content-Disposition` → 回落到「URL 末段 + `.bin`」 | ❌ `<id>.bin` |

而 `pick_target()` 里 `override`（预分配路径）的优先级高于 `cd_name`（真实文件名），
所以后面就算解析到了真名也用不上。

**改动**（`modules/clawfetch/clawfetch.py` · `_preassign_targets()`）：
探测到响应是网页（`content_type` 含 `html`）且**拿不到文件名**时，先
`resolve_html_page()` 解析出同域直链，再对直链做一次探测取 `Content-Disposition`；
取到就打印 `[批量] 链接 N 是网页中转页 → 已解析直链后取名:xxx.mp4`。
每条约多花一次 16 KB 页面请求，可忽略。

**验证**（mock 源站自带 `/download/` 中转页路由，`/stream/` 的文件头写的是
`filename="mock-payload.bin"`）

  → `9.mp4` / `10.mp4` / `11.mp4` ✅

## T. 任务记录「点封面就能播放」（2026-09-29）

|---|---|---|

  不限长度会把 `_1080_0.mp4` 末尾的 `0` 当成 id（第一版就踩了这个坑）。
- 剪枝：跳过 `venv / site-packages / node_modules / runtime / .git`，深度 ≤ 6。
  本机实测扫 3720 个文件 **0.034 秒**；索引是进程内缓存（TTL 5 分钟），
  索引未命中时按 15 秒节流重建一次（新下载的作品不必等 TTL）。
- 覆盖率：库里 1702 条 → 命中 1692 条（**99.4%**）。未命中的 10 条实测**文件确实不在磁盘上**
  （3 条 video + 7 条 gallery），不是索引漏找。

**PID 11448 就是它自己的父进程。** 父进程领了批量租约，却没把租约传给子进程，
子进程 `acquire_run("fast_dl")` 于是把「自己的父进程」认成了竞争对手，当场刹车。

### W2 三个 bug

#### bug 1（主因）：`kuaishou_fast_dl.py` 的拉起路径**漏传** `KS_RUN_TOKEN`

`kuaishou_headless.py` 有多条拉起子进程的路径，只有一条传了租约：

| 调用点 | 原状 | 后果 |
|---|---|---|
| `_resume_pending()` | `subprocess.run(cmd, env=_env)` ✅ 传了 | 只有 resume 模式能用 |
| `all` / 限量 N 个主线 | `subprocess.run(cmd)` ❌ 漏了 | **全量/限量必被自己拦死** |
| `_spawn_fast_dl`（新增） | 统一注入 `KS_RUN_TOKEN` | 结构上消灭「漏传」 |

子进程借用租约的语义是「父进程领的，我用」——`_inherited=True`，不写文件、不释放。
漏传时它读盘看到一把**活着的**锁，报出的持有者正是父进程，于是走「守卫主动刹车」：
**退出码 0**，任务中心显示成功，用户看到「下载成功，一个文件都没有」。

**离线铁证复现**（`tests/test_guard_run_token.py` A 段）：
不传 token 时子进程报 `{'ok': False, 'pid': <父进程 pid>, 'mode': 'batch'}`；
传上 token 后 `{'ok': True}`。**报出的"竞争对手"就是父进程，这是漏传无可辩驳的签名。**

修复：把所有拉起 `kuaishou_fast_dl.py` 的地方**收敛到一个 spawn 助手**：

```python
def _spawn_fast_dl(cmd):
    env = dict(os.environ)
    try:
        tok = ks_guard.current_token() if ks_guard else None
        if tok:
            env["KS_RUN_TOKEN"] = tok
    except Exception:
        pass
    return subprocess.run(cmd, env=env)
```

再加一道 **AST 栅栏**（C 段）：静态断言「所有拉起 `kuaishou_fast_dl.py` 的
`subprocess.run/Popen` 都带 `env=`」。只盯这一个目标脚本，不误伤 yt-dlp / powershell 那类。

起因是用户报「抖音下载速度太慢而且有下载失败的」。这一轮**先取证再改**，

### X1 现场：失败是**成簇**发生的，不是散的

任务 `bf863446014`（主页链接，8113 条待下载，`thread: 5`，`video_quality: original`）。

### X3 旧代码为什么把这 100 秒烧成 167 条永久失败

两个原因叠在一起：

1. **退避远短于封禁窗口**。候选轮扫是「每轮各试一遍候选」，轮间退避
   `1 + 2 + 5 = 8s`，而封禁窗口实测 **100s 量级** —— 4 轮全部落在窗口里。
2. **失败一旦落定就不再重来**。`_download_mode_items` 只统计主轮结果，
   没有第二轮；用户只能事后自己发现并手动补。

### X4 改动一：条目粒度的失败熔断（撞墙就全体刹车）

新增 `storage/file_manager.py::FailureBurstBreaker`：30 秒窗口内失败满 **10 条作品**
→ 全体 worker 停在闸门口冷却（首次 20s，每再撞一次翻倍，封顶 300s；
冷却期内不再翻倍），从最后一次失败起安静满一个窗口才把冷却时长收敛回基准。

**记账放在「条目」粒度上，不是 `download_file` 调用粒度上。** 这条很关键：
一次候选轮扫同一条作品最坏能产生 `4 候选 × 4 轮 = 16` 次下载失败，按调用记账
的话**一条死链作品自己就能凑满阈值**，把健康节点一起刹停。

- 记账点：`_download_aweme_assets` 的**传输**失败分支（视频候选链全灭、
  图集某张图失败、实况图失败）+ 主媒体完好落盘的 `_note_transport_success`。
- **内容层面的失败不记账**：没有可播地址、DRM 密文、媒体类型不支持 —— 那是作品
  本身的问题，拿去冷却只会拖慢整批。
- 「跳过」也不记账：跳过的是早就下过的作品，不代表源站现在通。

### X5 改动二：轮末补下失败条目

`BaseDownloader._recover_failed_items`：主轮跑完后给失败条目补跑
`failure_retry_passes` 轮（默认 2 轮，冷却 20s / 40s，封顶 60s，最多 4 轮）。
每轮重新走 `_should_download` + 候选构造，拿到的是**重新签名**的新地址，
不是上一轮已过期的那份。`UserDownloader` 与 `MixDownloader` 都接上了。

统计口径：自愈轮**不推进条目计数**（否则 8113 会被冲成 8114、进度条越界），
轮末由 `ProgressDisplay.revise_items` 把数字从「失败」挪到「成功」，
并**重打一行与 `advance_item` 同形的** `条目 N/M | 成功 … 失败 … 跳过 …`
—— 任务中心的百分比解析器（`_RE_DY_ITEM`）只认这一种形状，不重打界面会一直
停在自愈前的「失败 167」。

## Y. 任务记录页「查找重复视频」（2026-10-01）

起因：用户要在「任务记录（作品档案）」页加一个**查找重复视频并保留一个**的功能，
**抖音、快手一起扫**。这是一处**破坏性操作**（删文件），按「只读工具加删除」的规矩
先取证、再实现、用副本验证，真实数据一个字节没动（删除只进回收站）。

### Y1 先查「重复」到底指什么

抖音视频文件名带 19 位 `aweme_id`，快手文件名带 `photoId`（`[3x...]` 或
`YYYYMMDD_HHMMSS_<id>_...`），两套 ID 互不相通。逐类摸底（只读扫盘）：

| 判定 | 实测结果 |
|---|---|
| 字节完全相同（SHA-256） | **6 组 / 6 个冗余文件 / 约 40 MB**，全在快手 |
| 同作品 ID 但字节不同 | 大多是抖音**直播分段**（`_live_1..5` 同 aweme_id 不同内容）→ **不能当重复**；另有 1 组 `adapt_lowest` vs `normal_720` 同作品不同清晰度 |
| 跨平台同名 | 转码后字节不同，哈希不匹配 |

结论：**唯一能安全「保留一个」的判据是字节完全相同**。同 ID 分组会把直播分段、
不同清晰度误判成重复，一律不做。

### Y2 改动

- `webui/bridge_server.py`：
  - `_dedup_roots()` 精确列出抖音 + 快手全部视频根（不复用 `_media_roots()`，
    因为它会把 downloads/ 整目录当抖音根、连 downloads/kuaishou 一起卷进来还标错平台）。
  - `_dedup_scan()`：大小预筛 → 只对「同大小的组」做 SHA-256 → 每组定保留/冗余。
  - 保留规则：优先非辅助目录（`edge-manual-profile` / `login-profile`），再比体积大、
    时间新、路径字典序兜底。
  - `_recycle_files()`：PowerShell `Microsoft.VisualBasic FileSystem.DeleteFile(..., SendToRecycleBin)`，
    走 `-EncodedCommand`（UTF-16LE+base64），**回报用下标不用回显路径** ——
    否则 PowerShell stdout 按 GBK 输出、中文路径乱码，结果映射错位。
  - 三个路由：`POST /api/bridge/dedup/scan`、`GET .../status`、`POST .../delete`；
    删除路径必须落在已知根下，越界/不存在一律拒绝。
  - 文件头安全边界同步改成「写操作四处」。
- `webui/assets/js/api.js` + `pages/archive.js`：任务记录页加「查找重复视频」按钮
  （bridge 模式才显示），扫描进度弹窗 → 结果分组（保留/删除逐条）→ danger 确认弹窗
  （列后果，不是「确定吗」）→ 回收站。

## Z. 单作品链接下载不再计入「关注」（2026-10-30）

### Z1 现象与根因

用户要求：保留单作品链接下载，但它不该把作者塞进「关注」，关注列表的统计与
「一键更新」也不能被它干扰。

「关注」一直是**派生**的：抖音 `aweme` 表按 `author_name` 聚合、快手按台账落盘目录
聚合。任何入口（CLI、WebUI、手机下载、独立图形窗口）写进来的作品都会自动出现在

- 关注了这位作者，于是把他主页批量下下来；

### AA2 「只成功 6 个」——源站断了，但卡片把失败藏了

## AE. 抖音「收藏与喜欢」扫码成功却又弹新码（2026-11-01 11:10）

用户报：在「收藏与喜欢」点扫码登录，手机扫完码、确认后，网页又生成一张新二维码，
怎么都登不上。

### AE1 根因：临时 profile = 每次都是「新设备」

`AccountService._login_flow` 原来是这么起的：

```python
browser = await pw.chromium.launch(headless=False)
context = await browser.new_context(user_agent=UA, ...)   # 临时 profile，每次全新
await context.add_cookies(self._cookie_payload())          # 再把旧 Cookie 塞进去
```

三个问题叠在一起：

1. **每次登录都是全新设备**：`ttwid / UIFID / did / IndexedDB` 全部重置。抖音的扫码
   确认是跟「发起这张码的那台设备」绑的，服务端认不出来 → 直接把这次确认作废 →
   网页收到"失效"就又画一张码。**快手那边早就踩过同一个坑**，代码里写着：
   "空 context 里塞旧 Cookie 会出现「手机扫码成功、点了确认、网页却回二维码失效」"
   （见 `KsAccountService._open` 的注释）。抖音这半套一直没跟着改。
2. **UA 与 UA-CH 对不上**：UA 写死 `Chrome/139`，实测内核 `userAgentData` 是
   `Chromium/151`（headless 时甚至是 `HeadlessChrome`）。这是最容易被风控挑出来的特征。
3. **把会话搬到另一个浏览器**：`.cookies.json` 里 10:29 那次"成功"保存的会话，
   10:45 在读取通道里回 `status_code 8 用户未登录` —— 同一个 sessionid 在原浏览器里是好的。
   会话是跟设备/浏览器状态绑的，搬 Cookie 等于换了台设备。

### AE2 改动（`webui/account_service.py`）

- **扫码登录**：`launch_persistent_context(runtime/douyin-login-profile, channel="msedge",
  headless=False)`。固定 profile → 设备指纹跨次保留；系统 Edge → 真实 UA，不再伪造；
  **不再注入旧 Cookie**。
- **读取通道** `_ensure_page`：同一个 profile（有头、窗口挪到 `-32000,-32000`）。
