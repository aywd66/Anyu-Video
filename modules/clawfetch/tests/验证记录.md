## 已发现并修复的问题(测试驱动)

1. **206 续传大小口径**:初版把 Content-Range 总大小又叠加 offset,导致续传时进度显示 6MB/5MB、误报"传输不完整"。已修复:Content-Range 总数即最终大小;修复后断流续传一次通过。

## v1.4.1 源半死快速失败 + 同域串行 验证（2026-09-11 晚）

背景：用户 4 条真实链接全部失败——同属一条半死 trycloudflare 隧道；旧版对半死源（能连接但不发数据）要空等约 30 分钟才失败，且同域多链接并行会互相挤占源头。

修复：①全局无进度检测（STALL_ABORT_SEC，env CLAWFETCH_STALL_ABORT，默认 120s；连续两轮尝试零进度 → 快速失败并保留进度）；②同域链接自动串行、不同域并行；③中止收尾改总时限等待（消除逐线程 join 的时间放大）；④预检探测超时上限 10s。

场景验证（tests/runs/）：
| 场景 | 命令要点 | 结果 |
|---|---|---|
| 黑洞快失败 | mock --blackhole + CLAWFETCH_STALL_ABORT=12 -n 3 | 46.9s 干净失败，退出码 6，报“连续 2 次尝试无任何下载进度”，进度文件保留 ✓ |
| 保留进度复核 | 同上 -n 1 后核查目录 | .part 与 .part.meta 保留未隔离，提示“重跑同命令可续传” ✓ |
| 慢卡死（每新连接放行 64KB） | mock --stall-after 65536，阈值 12s | 137.4s 经 4 轮尝试后干净失败（修复前同场景约 30 分钟）✓ |
| 同域串行 | 2×20MB 同端口 -j 2 | 24.3s，2/2 成功，同域提示语正常 ✓ |
| 跨域并行 | 20MB+20MB 两端口 -j 2 | 12.2s，2/2 成功 ✓ |
| 真实环境 | fe019 链接，8 线程自动模式 | 1,802,719,649 字节（1.68GB）一次成功，速度 3~17MB/s，中途全量闪断被分段级重试自愈；SHA-256 8e242a6248b2195b33d9e6d4f0e86bc2efdb3ee46b91d939812c2b0893855ac3 ✓ |

结论：v1.4.1 把半死源的失败判定从 30 分钟级降到约 47 秒级（阈值 12s 时；默认 120s 下约 5 分钟内）；真实源恢复后多线程下载稳定可用。配套新增 mock 服务器 --blackhole 模式（HEAD 正常、正文零字节）用于复现“半死源”。

## v1.4.2 并发自适应改「双向」+ 续传时 --segments 生效 验证（2026-09-26）

### 起因：一次真实失败（E://zl 那份 818.91 MB）

链接是 File To Link Bot 风格的中转页 → `/stream/<token>`，托管在一条
 **trycloudflare 临时隧道**上。用户从手机端下发后失败，日志与台账如下。

| 尝试 | 并发 | 结果 | 已下 |
|---|---|---|---|
| 1 | 8 连接 | HTTP 520，133 秒 | 27.96 MB |
| 2 | 8 连接 | HTTP 500，42 秒 | **0 增长** |
| 3 | 8 → **16** 连接（自适应扩容触发） | HTTP 502，53 秒 | 33.47 MB |
| 4 | **23 连接** | 连接/读取超时，158 秒 | 63.39 MB（唯一一次有意义的进度是第 4 次，因为跑得久） |

一次运行里刷出 **72 次 HTTP 502、33 次「30s 无数据」读超时**。全程约 10 分钟、
共下 63 MB，实际聚合约 106 KB/s，最后 4 次尝试用尽，断点被隔离。

### 关键实测：并发在这个源站上是**负收益**

用同一链接、同一时刻做受控测量（每路只取 1 MiB，读 Range）：

| 并发 | 聚合速度 | 单段耗时 | 结果 |
|---|---|---|---|
| **1 连接** | **290 KB/s** | 3.5 s | 1/1 成功 |
| 4 连接 | 101 KB/s | 15.8 s | 3/4（1 段 30s 零字节超时） |
| 8 连接 | 168 KB/s | 17.8 s | 5/8（3 段 30s 零字节超时） |

也就是说：**单连接本该 48 分钟下完，并发把它变成了失败**。
另有对照：8 路并发两轮分别为 2353 KB/s 与 34 KB/s —— 这个源站极不稳定，
但"稳定"恰恰是下载最需要的性质，所以并发在这里不值得赌。

### 根因（两层）

1. **源站侧**：临时隧道只能同时喂很少几路。并发一多，多出来的连接拿不到带宽
   （表现为 30 秒零字节 / 502 / 500 / 520）。
2. **clawfetch 侧（真正要改的）**：自适应只会**加**连接，不会减。
   - 判"健康"用的是 `all(s["done"] > 0)` —— 每段滴到过一滴就算健康。
     818 MB 的源站上滴速 2 KB/s 也算"健康"，于是 8→16→32（实际 23 段）一路加。
   - 唯一的逃生门 `bailed`（串行源 → 回退单线程）被 `attempt == 1 and resumed == 0`
     锁死：从第 2 次尝试起永远打不开，而失败恰好都发生在第 2 次之后。
   - 而且那条逃生门是 `move_to_trash` + 重下 —— **靠丢掉已下进度换单线程**。
   - 附带：`--segments N` 在续传时被盘上的 meta 覆盖。用户照提示加
     `--segments 1` 也没用，仍会以 23 连接开局。
   - 附带：预检探测沿用 `--timeout` 且最多试 2 次，`-t 60` 会让**还没开始下载**
     就先等约 100 秒（批量模式早有 10s 上限，单链接模式漏了）。

### 改动

| # | 改动 | 说明 |
|---|---|---|
| 1 | 新增纯函数 `concurrency_starved()` / `retry_storm()` | 把"并发把源站喂哑了吗"变成**可测**的判据 |
| 2 | 新增 `coalesce_ranges()` | 碎洞合并。一个连接只能顺序读一段连续区间；洞太碎时"降到 1 连接"根本做不到，降档会原地打转（真踩过）。会重下被夹在中间的少量已完成字节，属刻意取舍 |
| 3 | 降档：`starved` 或「零进度 + 重试风暴」→ 连接数砍半 | 原地重切（`_swap_workers`），**进度全部保留**，取代原来"丢进度换单线程" |
| 4 | 升档收紧：只有「这一窗干净（无挨饿、无重试风暴）且吞吐确有收益」才加 | 快源偶发闪断不再被误判、也不会被判死刑 |
| 5 | `preferred_n` 跨尝试记忆 | 第 2 次尝试不再从 8 连接重学一遍教训 |
| 6 | 续传时 `--segments N`（含 auto 的目标并发）覆盖盘上旧布局 | 只收不放；否则用户的自我救援是空话 |
| 7 | 失败提示改向 | 分段重试/5xx 密集时明说"源站扛不住多连接，请用 `--segments 1`（进度会续传）"，而不是含糊的"增大 --timeout" |
| 8 | 探测超时上限 `PROBE_TIMEOUT_MAX`（默认 10s，可 env 调） | 三个调用点统一；`-t 60` 不再拖慢开局 |
| 9 | mock 服务器新增 `--slots N` | 模拟单通道源站：超出的请求**当场回 502**（不排队） |

### 验证

新增 `tests/test_serial_source.py`（离线、不联网、**19 项全绿**）：

- **判据**：钉在真实日志的数字上（8 段里 3 段零字节 → 判饿死；全零 → **不**判饿死，
  那是源站不通、降连接没用；重试风暴阈值 `max(2, N/2)`）。
- **端到端**（mock `--slots 2 --rate-limit 700`，18 MB）：
  - 修复后：退出码 0、SHA-256 一致、连接序列 **[8, 4, 2]**、进度全程保留、无隔离文件；
  - 修复前（同一场景、`git HEAD` 那份）：退出码 5、`服务器错误(HTTP 502)`、
    连接序列 [8, 8, 8]、**断点被移进隔离区**。
- **碎洞合并**：用**真实那份 23 段的 meta** 直接算 `_rescale_segments(x, 1)`，
  确认现在真的切出 1 个连接（修复前会切出 23 段，降档必然原地打转）。

### 已知限制（写清楚，别当成没有）

- 碎洞合并会重下夹在中间的已完成字节。这是"要更少连接"的必然代价
  （一个连接只能顺序读连续区间）。只在洞比目标连接数还碎时发生。
- 单线程路径（`--segments 1`）遇到**多线程分段旧进度**会判为不兼容并隔离重下
  （那是预分配到全长的文件），也就是说 `--segments 1` 无法复用多段断点。
  想保住多段断点，就让 auto 自己去降档。
- ⚠️ **预分配会真占磁盘**（本轮实测纠正了一个想当然的说法）：多线程路径是
  `open(part,"wb")` + `fh.truncate(total)` 预分配到全长的，而 NTFS 上**没标记
  稀疏属性**的预分配会真的分配出去。实测那份"只下到 2MB"的
  `电报搜索 @xkiqo.mp4.part` 名义 818.91 MB、占盘也是 818.91 MB
  （`GetCompressedFileSizeW` 查得，稀疏占比 0.0%）。
  → 一个"看着没下多少"的断点，在磁盘上可能就是整个文件那么大。清 `.part` 前先看一眼占用。
- 源站本身极不稳定时（同一链接 8 路并发两轮 2353 / 34 KB/s），
  再好的自适应也只能保证"不把自己搞死"，不能凭空变快。


## v1.4.2 补记：出网路径（`--proxy`）与源站侧分层实测（2026-09-26 下午）

上面那轮的结论是「单连接是这条链接唯一稳妥的方式」。补记两件当时没做透的事：
**到底走了哪条出网路径**，以及**源站到底卡在哪一层**。

### 一、出网路径：新增 `--proxy auto|none|URL`

起因：桥接服务用 `env = dict(os.environ)` 起子进程，把**外壳注入的**
`HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:12890` 原样继承了下来。那个代理属于
"启动桥接的那个外壳"（会随它消失），并不是用户本意；而 clawfetch 里 5 处裸
`urllib.request.urlopen` 完全按环境变量走 —— 于是「从这台机器直连那个 URL」
就悄悄变成了「绕到 127.0.0.1:<某个别人的端口>」。
**这一类问题最贵的地方是：你看不出它走了哪条路。** 所以先给一个开关：

```
--proxy auto   沿用系统/环境设置（默认，行为不变）
--proxy none   强制直连，忽略一切代理
--proxy URL    只走这个代理（如 http://127.0.0.1:7890）
```

实现是**整进程装一次 opener**（`urllib.request.install_opener`），而不是去改那 5 个
调用点 —— `install_opener` 换掉的就是 `urlopen` 内部用的全局 opener，所以所有调用点
自动生效、不会漏。另外每次运行都打印一行 `[代理] auto(沿用系统/环境设置:…)`，
把"实际走了哪条路"摆在明面上。

配套改动在 `modules/douyin/webui/bridge_server.py`：直链任务起子进程前用
`strip_proxy_env()` 摘掉 8 个代理类环境变量（大小写两种写法都覆盖），
并在任务日志里留一行说明摘掉了什么、以及要用代理时怎么办。

- ⚠️ 桥接是**常驻进程**，改完**必须重启**才生效。
- 摘掉 env **不等于**禁用代理：Windows 上 urllib 读不到环境变量时会继续读
  **系统代理**（注册表 `ProxyEnable`/`ProxyServer`），所以自己开了 Clash 之类
  「系统代理」的用户不受影响 —— 被摘掉的只是外壳临时注入的那一份。
- 改动半径刻意只落在**直链**这一条线上：抖音/快手本来就要走用户自己的网络设置。

> 一个 CPython 细节（写断言时踩到的）：`ProxyHandler({})` 的 `*_open` 方法是在
> `__init__` 的 for 循环里逐个 `setattr` 的，代理表为空时循环体不执行 →
> 这个 handler 一个钩子都没有 → `OpenerDirector` **不会把它登记进 handlers**。
> 所以"直连"在自查里表现为 **opener 上找不到 ProxyHandler**，而不是"找到了但它是空的"。
> 断言写成后者会一直是红的。

### 二、源站侧分层实测（这条链接现在到底有多糟）

`telecharger-album-plc-administered.trycloudflare.com`（Cloudflare 临时隧道）
背后的服务器，逐层实测：

| 层 | 结果 |
|---|---|
| DNS | ✅ 0.01s，解析到 `104.16.230.132` / `104.16.231.132` |
| TCP 443 | ✅ 0.23s 连上 |
| TLS 握手 | ✅ 0.47s，TLSv1.3 |
| **HTTP 响应** | ❌ **6 次里 5 次收不到响应头**（各在 15s 超时），1 次 7.88s 成功返 206 |

→ 不是 DNS、不是被墙、不是 TLS、也不是客户端：**卡在"请求发出后源站不出声"**。

再看"多等一会儿"会不会来（单连接、60s 超时、3 次）：

| 次数 | 首字节等待 | 之后 |
|---|---|---|
| 1 | **19.94s** | 0.51s 交完 256 KiB（≈0.5 MB/s） |
| 2 | >60s（超时） | 无 |
| 3 | >60s（超时） | 无 |

结论：**首字节延迟在 0～>60s 之间剧烈抖动**；一旦开始给数据，速率其实不差。
短超时（`-t 20`）会让单次尝试经常失败 —— 而失败信息只写"超时"，看不出是"源站不出声"。

> ⚠️ **这一小节当时还写了「818.91 MB 在这种抖动下实际上不可能下完（成功率约 1/3）」——
> 这句话是错的，已被后续实测推翻。** 详见下面的「五」。它错在把一个**十分钟采样窗口**
> 当成了永久性质：源站的瓶颈是**突发式限流**，不是"永久不出声"。窗口差的时候确实
> 三次里中不了两次，但窗口好的时候它能**连续 25 分钟不停给数据**。

**再往下切一刀：卡的是"文件流端点"，不是隧道、也不是带宽。**
同一个源站、同一条隧道，换个路径再测一轮：

| 请求 | 结果 |
|---|---|
| `GET /download/<tok>`（HTML 中转页）×3 | ✅ **3/3 成功，首字节 1.04 / 1.15 / 1.43 s** |
| `GET /stream/<tok>`，Range 256 KiB ×3 | ◐ 2 成功（首字节 **30.89 / 16.96 s**）、1 在 30s 超时 |
| `GET /stream/<tok>`，Range **1 字节** ×2 | ◐ 1 在 **17.09 s** 后返回 1 字节、1 在 30s 超时 |

→ **隧道是活的、HTML 页 1 秒就回**，只有**文件流端点**在卡。
而且"只要 1 个字节"也要等 17 秒 —— **这不是带宽问题，也不可能是"多连接互相挤占"**
（1 字节没有带宽可言），而是**文件流处理端自己串行阻塞**（最像的情况：同一后端进程
正在处理另一个长下载，或它在慢慢读一个远端文件）。
这同时解释了"为什么降到单连接也快不起来"：单连接能做的只是**不被别人的排队连累死**。

所以这条链接当时的定性是：**源站侧问题（文件流端点串行阻塞），客户端改不了它的速度。**
正确的应对是**单连接 + 短超时 + 大量重试 + 进度保留**（客户端能做的只有"别把自己搞死、
别白下"）—— 而不是放弃。这一点已被下面的「五」证实。

### 四、如实记录一处**不稳定**的对照

第一版写的是「修复前：退出码 5、`[8,8,8]`、断点被隔离」。重跑时同一场景
**修复前也成功了**（`[8,8,8]`、退出码 0）—— 因为源站快慢本身是随机的，
旧代码在源站"心情好"的时候也能把 18 MB 拖完。

所以：**A/B 对照是时序相关的，不能拿一次结果当铁证。**
真正每次都能过的断言是「修复后一定收敛到少数连接、且不丢进度」；
"修复前一定失败"只在这台机器忙、或源站慢的时候成立。
想稳定复现旧代码的失败，把 mock 的 `--slots` 调小、`--rate-limit` 调低，
或把 `SIZE` 调大。

### 五、这份 818.91 MB **最终下完了**（2026-09-26 14:15，推翻上一条结论）

上一条"客户端修不了、实际上不可能下完"的判断，被一次**耐心重跑**直接推翻。

**用的命令**（就是上面那轮我给出的"单连接逃生"方案，一字未改）：

```
clawfetch.py "https://telecharger-album-plc-administered.trycloudflare.com/stream/c3efc4f8263a3e48" \
    -o E://zl --segments 1 -n 100 -t 20 --backoff 2
```

**结果**：18 次尝试、**44 分 59 秒**、退出码 0。

| 项 | 值 |
|---|---|
| 文件 | `E://zl//电报搜索 @xkiqo.mp4` |
| 大小 | 858 694 563 字节（818.91 MB），与服务器报告一致 |
| SHA-256 | `9a4459cf…b6b8eb`（**另用独立 `hashlib` 脚本复算过，一致**） |
| 成功那次尝试的时长 | **1507 秒**（约 25 分钟**不间断**），从 5.94 MB 一口气拉到 818.91 MB |
| 等效均速 | 约 **540 KB/s** |
| 失败尝试数 | 17 次（502 / 20s 无数据 / 读取超时），**进度一次都没丢** |
| 最终 `.part` / `.part.meta` | 无残留（收尾时 `.meta` 被改名成 `.part.meta.<stamp>.done`） |

**这次成功教了三件事：**

1. **源站不是"死了"，是"突发式限流"。** 前 17 次尝试里进度从 1.00 → 5.94 MB 磨了
   将近 20 分钟（每次 20s 超时都要重排队）；第 18 次一进去就**连续给数据 25 分钟**。
   所以瓶颈的形态是「窗口差时频繁归零，窗口好时能持续输出」，而不是"永久不出声"。
2. **短超时（`-t 20`）在这里是优点，不是缺点。** 我一度建议"加大到 `-t 90`"——
   那是错的：卡住的请求要等 90 秒才被放弃，而每次放弃都要重新排队。**20 秒果断切断 +
   立刻重来**，撞上源的"好窗口"的概率反而高得多。`-n 100` 提供了足够的重试预算。
3. **"进度保留 + 自动续传"是这次能成的真正前提。** 17 次失败累积的 5.94 MB 一滴没丢，
   第 18 次是从 5 945 920 字节接着下的。旧代码在第一条逃生门上就会 `move_to_trash`
   把这几 MB 丢掉、并因 `attempt == 1` 锁死而再不会开第二次。

**结论修正**：这条链接的正确处置是「单连接 + 短超时 + 大量重试 + 耐心」，
**不需要**等源站"恢复"、**更不需要换源**。客户端改不了它的速度上限，
但能保证"不白下、不放弃" —— 而这一点就足够把 818.91 MB 拿下来。
