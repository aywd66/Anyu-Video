## 风控节奏（2026-09-25 补充，**这一节的结论和上面「等几分钟重试」相反**）

### 实测数据

| 时间 | 干了什么 | 结果 |
|---|---|---|
| 09-24 20:24 | 收集 55 个 + 连调 55 次详情接口 | ✅ 55 成功、0 失败 |
| 09-25 14:13 | 连调 12 次详情 | ✅ 12 成功、0 失败 |
| 09-25 16:53 | **深滚收集 1790 个作品**，随后开始调详情 | ❌ 第 12 次起全是 `status_208005` |
| 09-25 21:03 / 21:19 | 又试了两轮 | ❌ 1/19、0/11，全线失败 |
| 09-25 21:58 | **单条模式**（同一个 `fetch('/graphql')`、同一套 cookie） | ✅ 拿到 720p 直链并下载成功 |

### 三条结论

1. **不是「接口配额只有 2 个」。** 旧注释里那句「一口气请求到第 2 个起就返回 208005」
   是在**已被封的状态下**测出来的，把「已封」误当成了接口的固有属性。
   连调 55 个、12 个都 0 失败。
2. **撞墙后「单条还能跑」是硬事实，但「封的是形态不是账号」只是推断。**
   单条模式确实在「被封」5.4 小时后用同一个接口成功了 —— 但那次**同时**满足了
   「换了新页面」和「冷却已过」两件事，两个变量分不开，所以**阈值到底绑在账号上
   还是绑在单个页面上下文上，至今没有定论**（见下「多开窗口」）。
   能确定的只有一条：**短时间内的总请求量**是触发条件
   （收集 1790 个 + 接着调详情 = 撞墙；只收 55 个时 55 次详情 0 失败）。
3. **撞墙后短时间内重试毫无意义，而且可能更糟。** 实测 4h26m 未解；
   每重试一轮就多打一轮请求，可能把惩罚窗口往后推。

### 现在的做法：交给守卫（`tools/ks_guard.py`）

不再靠「多试几次」，而是**不让程序有机会一次要几千个**：

- **冷却**：撞墙即把截止时间写盘（首次 90 分钟，之后指数退避，封顶 24 小时）。
  冷却期**批量模式直接收工**（退出码 0，不是失败），并说清几时再来。
  单条模式不拦 —— 实测它在冷却期仍可用。
- **当日预算**：默认每天最多收集 400 个、调 400 次详情接口，跨进程累计、按自然日重置。
  `all` 的「全量」语义被改成「今天这份量」。
- **批量独占**：同一个账号同一时刻只允许一个**批量**进程。你再开一个窗口跑批量，
  第二个会被当场拦下（退出码 0）并告诉你是谁在跑。理由见下。

### 风控有两种长相（2026-10-03 踩到，务必知道）

上面这套冷却能生效，前提是**「撞墙了」这件事被正确识别**。这里踩过一个坑：

刹车判据是「连续 12 个 `status_208005`」，但快手挡人的时候**不一定给这个码** ——
有时 `visionVideoDetail` 整个字段是空的，`status` 读出来是 `None`（台账里
reason 写成 `status_None`）。**那也是风控。**

当天台账里的真实顺序是：

```
208005×9 | None×2 | 208005×1 | None×6 | 208005×8
```

纯 `208005` 的**最长连续只有 9**。而旧代码只把 `208005` 计入计数、遇到 `None`
就清零 → 条件永远达不到 → `note_block()` 一次都没被调用 → 守卫里的
`block_count` 恒为 0、`blocked_until` 恒为 0.0 → **跨进程冷却从未落盘**。
于是每一轮都重新撞墙、重新失败二十多次，而日志里**一条冷却记录都没有**，
看起来就像「偶发网络问题」。

修法（`kuaishou_fast_dl.py` 的 `RISK_STATUS` / `_is_risk_status`）：两种信号一起
计数，且不因 `status_None` 清零；`status_1040`（内容已删除）仍**不算**风控 ——
它跟风控无关，误判会让人白等 90 分钟。另外两条配套：

- 风控信号**不写进失败台账**。这些作品本身没问题，只是这一轮接口被挡着，
  写进去会让「失败清单」凭空多出几十条，看着像片子坏了。
- 一轮里只要出现过风控信号，就**不调** `note_ok()` 清冷却。旧判据只看
  「有没有抢到几个直链」，等于每次都给自己提前解封。

- **状态落点固定**在 `data\kuaishou\risk_state.json`，**刻意不跟产物目录走** ——
  否则「换个产物目录」就能绕过刹车（当天真踩了这个坑）。

### 多开几个窗口并行跑，会不会更快？

**不会，而且更糟 —— 这是本轮的结论。**

快手这道风控认的是 `did` cookie（设备 ID）。同一个登录态在几个窗口里是**同一份身份**，
不是几份额度。多开窗口只做到两件事：

1. 当日额度被两个进程**各领一份**（预算本身是「读-判断-写」，不是原子的：
   两个进程都读到「还剩 400」→ 实际打出去 800），守卫被自己的第二个窗口绕过去；
2. 把「一次一个的温和串行」变成「几路并行」—— 而**并行猛打正是 09-25 撞墙的形状**。

> **唯一可能翻盘的情况**：如果阈值其实绑在「单个页面上下文」上，多窗口就真的能 n 倍。
> 这与上面第 2 条结论是同一个未定论的问题。仓库里留了取证工具：

```powershell
# ① 基线：单页面串行 45 个
python modules\kuaishou\tools\ks_granularity_probe.py --mode serial --total 45
# ② 等冷却过去后，轮转：3 个页面 × 每个 15 个（总请求数与 ① 相同）
python modules\kuaishou\tools\ks_granularity_probe.py --mode rr --pages 3 --per-page 15
```

轮转顺序是 A,B,C,A,B,C… 所以**账号看到的请求速率和单页面串行完全一样** ——
这才把「粒度」从「速率」里隔出来。判读：① 拿到基线 Q，② 看总数落在 Q（账号级）
还是 3Q（页面级）。会真实消耗当日额度，且大概率再触发一次冷却 —— 它就是去撞阈值的。

**在拿到结果之前，守卫按更保守的那一面（账号级）行事。**

### 多个 ck / 多登几个账号，有没有用？

**只有拿到「新的设备身份」才有用，多登账号本身没用。**

快手 PC 站有**两个各自独立**的身份 cookie：

| cookie | 是什么 | 同一 profile 里换号登录 |
|---|---|---|
| `did` | **设备** ID（36 位，形如 `web_59262ae3…`） | ❌ 不变 |
| `userId` | **账号** ID（10 位） | ✅ 变 |

所以在同一份浏览器 profile 里登出、再登另一个号，`userId` 变了、`did` **没变** ——
在平台眼里还是同一台设备。守卫按 **`did`** 分桶，于是：

| 做法 | `did` | 限额 | 结果 |
|---|---|---|---|
| 同一设备换账号 | 不变 | 同一个桶 | ❌ 不加额度 |
| **换一份 profile**（`KS_PROFILE`） | 变了 | 各自一桶 | ✅ 各一份额度，可并行 |
| 换台机器 / 别处抓的 ck | 变了 | 各自一桶 | ✅ 同上 |

**为什么按 `did` 而不是 `userId` 分桶：猜错的代价不对称。** 万一平台其实按设备判，
按账号分桶就等于把刹车拆了（同一台设备两个号各领 400 → 实际打出去 800）；
反过来只是慢一点，没有损失。所以取保守的那一面。

**再开一路的正确做法**（需要另一份设备身份，也就是另一个 profile 目录）：

```bat
set KS_PROFILE=E:\录屏\ks-b
runtime\kuaishou-env\Scripts\python.exe modules\kuaishou\tools\kuaishou_login.py
```

登完再开一个窗口、带上同一个 `KS_PROFILE` 跑下载即可。两个桶的**额度、冷却、
租约都互不干扰** —— 租约也跟着桶走（`run.<桶>.lock`），不再是全项目一把锁。

**先看清自己有几个桶**：

```bat
runtime\kuaishou-env\Scripts\python.exe modules\kuaishou\tools\ks_ident.py
# 第一份登录态要补登记一次（只这一次，之后启动纯查 JSON、不开浏览器）：
runtime\kuaishou-env\Scripts\python.exe modules\kuaishou\tools\ks_ident.py --register
```

它会把每份登录态的 `did`/`userId` 读出来、算成桶、和当天额度对起来，
直接告诉你「现在有几个桶、多登号到底有没有收益」。

> ⚠️ **一个本机测不出来的变量**：如果平台还有 cookie 之外的指纹（canvas / 字体 /
> 出口 IP），这些桶在服务端**可能仍然被合并**。只能靠实际撞墙情况判断 ——
> 所以别一上来就把每路都开满，先让第二路跑小批量。别碰多号的风险换速度这笔账，
> 得你自己认：限流是临时的，被判定成批量抓取不是。

### 想全量一个几千作品的号，只有一条路

**拆到多天。** 8191 个作品按默认额度约需 21 天，每晚跑一次即可，台账保证不重下。
这是刻意的取舍：换取的是「日常使用几乎不会再撞风控」。

真要放宽：`KS_MAX_COLLECT_PER_DAY` / `KS_MAX_DETAIL_PER_DAY` 环境变量，
或者整套关掉 `KS_GUARD_OFF=1`（不建议）。
想真的多开一路 → **换一个桶**（`KS_PROFILE` 指向另一份登录态，见上一节）；
确实要在**同一个桶**里并行：`KS_ALLOW_MULTI=1` 放行独占检查（你清楚风险时再用）。

### 顺带修掉的一个泄漏

任务被取消走的是 `taskkill /F`，`atexit` 不执行 → 调试 Edge 会留在系统里
（实测 9 个进程、约 250MB，还把 `edge-manual-profile` 锁住）。
现在冷却刹车那条路径也会顺手清理它；入口也不再复用上一次运行留下的脏页面
（那个页面可能已经挂着验证浮层，在它上面发请求会一直拿到 208005）。
